- **GDPR erasure is executed, not just recorded (2026-08)** — `compliance_deletions` has carried an `executed` status and an `executed_at` column since Phase 13.5, and **nothing ever set either one**. Every reference to the model was request / list / cancel; api-core had no Celery beat and no worker process, so the only thing that ever drained `background_jobs` was `POST /admin/jobs/run-once`, an endpoint whose own docstring says it is for tests. A learner could request erasure, the UI would say "scheduled", the date would pass, and the row sat there forever. **The Phase 13.5 line below overstates what shipped** — read "schedules deletion 30 days out" as exactly that, a schedule with no executor, until this session. Now: `services/erasure.py` + two handlers (`compliance.delete.sweep` finds due requests and enqueues, `compliance.delete.execute` carries one out) + `worker.py`, a daemon added to compose as `api-core-worker` that drains the queue and sweeps every 5 minutes (and once at boot, so a restart catches anything that came due while it was down). **It anonymises rather than deleting the row, and the schema is why**: 143 FKs point at `users` (99 CASCADE, 30 SET NULL, 14 NO ACTION); the NO ACTION ones (`courses.instructor_id`, `grades.graded_by`, `items.created_by`, …) make `DELETE FROM users` fail for anyone who ever authored or graded anything, and `files.uploaded_by` / `notebook_files.uploaded_by` **cascade**, so deleting an instructor would delete the course files their students still use. One person's Art. 17 right must not destroy another person's records. So every identifying column is overwritten (email → `erased+{deletion_id}@erased.invalid`, unique because `unique_email_per_org` is real; password → a non-verifying sentinel; phone/bio/DOB/MFA/tokens → NULL) and `is_active=false` invalidates any JWT they still hold via `get_current_user`. Child rows are classified from the live `pg_constraint` at run time, not a hand-maintained list: `user_id`/`student_id`/`owner_id`-style columns are purged, `*_by`/`assigned_to`/`instructor_id`-style columns are kept pointing at the redacted row, and **anything matching neither is reported as `unclassified` rather than silently kept or deleted** — `test_erasure.py` asserts that list is empty for the current schema, so a new user FK with no policy fails CI instead of quietly leaving personal data behind. That gate immediately earned its keep: it surfaced 12 unclassified columns on the first run, each now an explicit decision. **14/14 tests pass** (8 pure classification + 6 against real Postgres) and the whole path was verified live end-to-end: a throwaway learner with a notification and an overdue request went from `e2e-erasure@example.test` / phone / bio / 1 notification / `scheduled` to a tombstoned email / NULL / NULL / 0 notifications / `executed`, with a PII-free `compliance.delete.execute` audit event and a job result recording `rows_purged: 1`, `tables_retained: 45`, `unclassified: []`.
